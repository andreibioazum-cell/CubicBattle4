# Firebase

Realtime Database + Firebase Auth (e-mail/пароль). Служебного бэкенда нет —
клиенты общаются с базой напрямую по REST, поэтому безопасность держится на
правилах и подписи запросов токеном.

## Это НЕ Gmail и не настоящая почта

Игрок **не регистрируется через Google/Gmail** — Google-аккаунт вообще не
нужен, браузер не открывается, письма не отправляются, подтверждать e-mail
не надо. `<ник>@cb4.game` — это просто внутренняя метка аккаунта **самой
игры**: у Firebase Auth провайдер «e-mail/пароль» требует строку-логин, и мы
скармливаем ему наш служебный адрес вместо выдумывания своей системы имён.

Что видит игрок: ровно то же, что и раньше — экран «Введите ник и пароль»
внутри игры. Больше ничего. Служебный аккаунт в Firebase Auth (пароль =
игровой пароль + внутренний суффикс) игра создаёт сама, молча, при первом
входе. Сменить «e-mail» или «пароль Firebase» руками игрок не может — да и
некуда: это не почта.

Зачем это нужно: только владелец такого токена проходит в базу (правила
пропускают лишь `@cb4.game`-аккаунты из password-провайдера), а создать их
может только наша игра — API-ключ ограничен пакетом `com.cb4`.

## Что изменилось (почему так)

Раньше правила были открытыми, а URL базы лежал в репозитории:

- `users` читался кем угодно — **пароли всех игроков лежали в открытом виде**
  и выкачивались одним GET-запросом;
- `event`, `bans`, слоты и чат писались кем угодно — базу можно было затереть
  или завалить запросами (то самое «дудосят»);
- клиент сам флудил: слал PUT своего состояния 16 раз в секунду, даже стоя
  на месте, и при сбое сети бился в сервер каждые 300 мс.

Теперь:

1. **Читать и писать базу может только наше приложение.** Каждый запрос
   подписан `?auth=<idToken>` (Firebase Auth). Токен выдаётся по ключу API,
   который в Google Cloud Console ограничен нашим Android-пакетом `com.cb4` и
   SHA-1 подписи APK — чужое приложение или curl ключом воспользоваться не
   может.
2. **Паролей в базе больше нет.** Пароль проверяет Firebase Auth, запись
   `users/<ник>` хранит только прогресс. Менять свой прогресс может только
   владелец ника (правило сверяет e-mail токена с ником).
3. **Структура данных защищена правилами**: типы и диапазоны всех полей
   проверяются, «сломать» базу мусорной записью нельзя. `event` и `bans`
   пишут только два админских аккаунта (проверка на стороне сервера, а не
   только в клиенте).
4. **Клиент перестал флудить**: если состояние игрока не меняется, PUT не
   отправляется (heartbeat раз в 2.5 с держит слот живым), чистка чата — раз
   в 5 с, а при ошибках сети пауза растёт экспоненциально (300 мс → 8 с) и
   не добивает упавший сервер.

Правила — в `firebase.rules.json` (публикуются из консоли или
`firebase deploy --only database:rules`).

## Переход (нужно сделать один раз)

1. **Firebase Console → Authentication → Sign-in method → включить
   e-mail/Password.** Это НЕ Gmail и не регистрация через Google: игрок
   по-прежнему вводит только ник и пароль внутри игры, никаких писем и
   подтверждений нет. Аккаунты создавать заранее не нужно: приложение
   регистрирует их само при первом входе (служебный логин `<ник>@cb4.game`,
   пароль — игровой пароль игрока + внутренний суффикс, так что короткие
   игровые пароли проходят минимум в 6 символов Firebase).
2. **Настройки проекта → General → Web API Key** — скопировать ключ.
3. **Google Cloud Console → APIs & Services → Credentials** → у этого ключа
  _restrictions_: Application restrictions → Android apps → добавить пакет
   `com.cb4` и SHA-1 отпечаток подписи (и debug, и release). Это то, что
   делает ключ пригодным только для нашего приложения.
4. Вписать ключ в `game/scripts/core/config.ds`:
   ```dimscript
   string FB_KEY="AIza..."
   ```
   Пока ключ пуст, клиент работает по-старому (переходный режим для уже
   собранных версий).
5. Опубликовать новые правила из `firebase.rules.json`.
6. **Выпустить новый APK** и раздать его: старые версии после публикации
   правил в онлайн не зайдут (запросы без токена получают 401/403 — это и
   есть защита в действии).
7. Один раз вычистить старьё из базы:
   - у старых записей `users/<ник>` удалить поле `pass` (консоль:
     Project → Realtime Database → Data, или скриптом по списку ников);
   - сменить пароли админов (`ADMIN_PASS`/`ADMIN2_PASS` в config.ds):
     старые лежали в открытом репозитории.
8. Рекомендуется: **App Check** (Play Integrity) для Realtime Database и
   бюджетное оповещение в Google Cloud — от остаточного риска перебора и от
   сюрпризов в счётах.

Если поменяете админские ники (`ADMIN_NICK`/`ADMIN2_NICK` в config.ds) —
замените их и в `firebase.rules.json` (строки `@cb4.game` в правилах
`event` и `bans`).

## Ники

В защищённом режиме ник — латиница, цифры и `_` (1–16): из ника собирается
e-mail аккаунта. Кириллические ники в новом режиме не регистрируются —
клиент честно отвечает «ник недопустим».

## Правила (суть)

В базу пускаются **только аккаунты самой игры** — служебные `@cb4.game` из
password-провайдера (проверка `gameUser()`). Google-аккаунты, анонимные
токены, токены других провайдеров и вообще любые чужие ключи отсекаются ещё
на входе. Поверх этого:

```json
{
  "rules": {
    "functions": {
      "gameUser":  "…@cb4.game + provider == 'password'",   // только наша игра
      "adminUser": "…два админских e-mail…"
    },
    ".read": false, ".write": false,
    "users/$nick": {
      ".read": "gameUser()",                                  // таблица лидеров
      ".write": "gameUser() && email == $nick@cb4.game",      // только свой ник
      "pass": { ".validate": false }                          // пароли не хранятся
    },
    "rooms/$room/players/$slot": { … },   // gameUser(), поля проверены
    "rooms/$room/chat/$msg":     { … },   // gameUser(), текст ≤ 96 символов
    "bans/$nick":  ".write": "adminUser()",   // ban/unban — только админы
    "event":       ".write": "adminUser()"
  }
}
```

То есть: читать и писать игру может **только из нашей игры** — чужой клиент
даже с украденным токеном Google в базу не попадёт, а свой прогресс каждый
игрок пишет только под своим ником.

Чтение `users` оставлено игровым аккаунтам ради таблицы лидеров: это видно
только пользователям нашего приложения, и паролей там больше нет.

## URL и структура

В `game/scripts/core/config.ds`:

```dimscript
string FIREBASE="https://...firebaseio.com", ROOM="main"
string FB_KEY=""   // Web API key (ограничен пакетом com.cb4)
```

```
users/<ник>/ nick, cups, candies, cls, azum, santa, level, levels, ...
rooms/main/
  players/0..3/ uid, nick, x, y, angle, hp, alive, seq, px,py,pdx,pdy,punch, sx,sy,sdx,sdy,snow, cls, level
  chat/<key>/ uid, nick, text
bans/<ник> true = забанен
event/ 0=нет, 1=диско, 2=снег
```

## Как выглядит вход клиента

1. `POST identitytoolkit.googleapis.com/v1/accounts:signInWithPassword?key=FB_KEY`
   c `email = <ник>@cb4.game`. Нет аккаунта → `accounts:signUp`
   (регистрация). Неверный пароль → `NET_LOGIN_WRONG_PASS`.
2. idToken живёт ~1 час; по истечении клиент молча обновляет его через
   `securetoken.googleapis.com/v1/token` и повторяет запрос.
3. Каждый запрос к базе получает `?auth=<idToken>`; 403 означает отказ
   правил (в лог пишется причина).

## Админ

Админов двое, право даёт вход под своей парой «ник + пароль» (это теперь и
аккаунт Firebase Auth, поэтому правила пропускают их записи в `/bans` и
`/event` только у них):

- `Dimasi4ek229` — красный ник (главный админ);
- `qwertyuiopaj1234` — голубой ник.

Команды в чате (только для админа): `event 0|1|2`, `ban <ник>`,
`unban <ник>`. Забаненный не заходит в онлайн и выкидывается из комнаты;
список `/bans` клиенты перечитывают раз в 2 секунды.

### Админ-панель (`index.html`)

Открывается прямо из браузера (файл или GitHub Pages): вход тем же ником и
паролем, что и в игре, дальше — снимок базы, поиск мусора (левые корневые
узлы, чужие поля в `users`/`rooms`, спам и взлом в чате, мёртвые слоты) и
быстрое удаление выбранного — Firebase REST не умеет батч, поэтому панель
схлопывает выбранные узлы (если по снимку выбраны ВСЕ дети узла, вылетает
целиком родителем одним DELETE) и гоняет оставшиеся запросы параллельно,
10 одновременно; плюс `event`, баны и выгрузка резервной копии.

Две вещи, из-за которых панель «не пускает»:

1. **Суффикс пароля.** В Firebase уходит не игровой пароль, а
   `пароль + FB_PASS_SUFFIX` (сейчас `|cb4v1`, см. `net.c`). Значение в поле
   настроек панели обязано совпадать с ним, иначе Firebase отвечает
   `INVALID_LOGIN_CREDENTIALS`. Панель сама перебирает известные варианты
   (`|cb4v1`, `#cb4`, без суффикса), так что вход проходит даже с чужим
   значением в поле — но если суффикс в игре поменяли, добавьте его и сюда.
2. **Ограничения API-ключа.** Ключ из `config.ds` ограничен Android-пакетом
   `com.cb4`; из браузера Google такой запрос может не пустить (403
   `PERMISSION_DENIED`). Для панели заведите отдельный ключ с ограничением
   по HTTP-referrer страницы панели. Кнопка «Проверить ключ» в настройках
   панели показывает, доходит ли запрос до Firebase.

Если все варианты не подошли, панель предлагает `accounts:signUp` — так же,
как `fb_sign_in()` в `net.c`: аккаунта нет → он создаётся, аккаунт есть →
Firebase отвечает `EMAIL_EXISTS`, то есть дело в пароле.

Правила из `firebase.rules.json` дают админам (`adminUser()`) ещё и запись в
чужие `users/$nick` и в левые корневые узлы (`"$other"`) — без этого панель
видит мусор, но удалить его не может. После правки файла правила нужно
**опубликовать** (Firebase Console → Realtime Database → Правила), сам по
себе файл в репозитории на базу не влияет.

ходил **только** с `?auth=` (`rtdb_no_auth == 0`).
