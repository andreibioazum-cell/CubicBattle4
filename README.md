# Gig1.0 / DimScript

Минимальный Android-движок и компилятор DimScript в C.

## Структура игры

```text
game/
├── game.ds                 # точка входа
├── player.ds               # дополнительные модули (необязательно)
├── assets/
│   ├── fonts/DejaVuSans.ttf # TTF шрифт игры
│   └── player.png          # PNG и другие ресурсы
└── AndroidManifest.xml
```

Сгенерировать `game/game.c`:

```sh
python3 gen.py
```

Показать сгенерированный C-код в логе можно только при необходимости:

```sh
python3 gen.py --dump
```

## Многофайловые игры

DimScript поддерживает C-подобные include-директивы. Путь считается от файла,
в котором записан include:

```c
#include "player.ds"
#include "modules/enemies.ds"
```

Include может быть вложенным. Каждый файл подключается только один раз, а цикл
в include выдаёт понятную ошибку. Старый режим тоже сохранён: при передаче папки
все верхнеуровневые `*.ds` в ней компилируются вместе.

## Строки, циклы и объекты

Строки — обычные значения C-строк, а `+` компилируется в настоящую
конкатенацию. Специального числового `ds_str_cat` больше нет:

```text
str title = "Score: " + floor(score)
str message = title + " / " + ds_num_to_string(10)

for (num i = 0; i <= 10; i += 1) {
    ds_log("i: " + i)   // вывод в лог (print/printn/prints удалены)
}
```

Переменные, объявленные в скрипте, компилируются в типизированные C-поля и
локальные переменные. В игровом цикле это прямой load/store, а не вызов поиска
`ds_read` в хэш-таблице. Хэш-таблицы по-прежнему доступны для динамических
данных через `T_get`/`T_set`; они растут автоматически и имеют versioned lookup
cache.

Для игровых сущностей можно использовать простые объекты:

```text
object Player {
    num x = 0
    str name = "player"

    fn init(num start) {
        self.x = start
    }

    fn move(num dx) {
        self.x += dx
    }
}

Player player = new Player(100)
```

Компилятор генерирует `struct Player`, `ds_new_Player`, `ds_free_Player` и
прямые вызовы методов. Поля объекта не хранятся в хэш-таблице.

## Software Renderer и TTF

Рендерер использует нативный software path Android: `ANativeWindow` блокируется
один раз на кадр, после чего скрипт формирует список команд, а `graphics.c`
растеризует его в буфер в правильном порядке. `rect`, `circle` и `ring` используют
быстрые заливки горизонтальных span-ов; непрозрачные PNG при масштабе 1:1 копируют
целые строки через `memcpy`. Нет generic-операции на каждом пикселе для обычных
примитивов и нет зависимости от OpenGL/EGL.

Шрифт по умолчанию — `assets/fonts/DejaVuSans.ttf`. Для другой игры положите
свой TTF по этому пути или измените путь в `graphics.c`. TTF разбирается и
растеризуется в сглаженный атлас один раз при первом вызове `text`; кадры используют
готовые glyph-ы и батч команд. `stage_assets.py` копирует вложенную папку `fonts/`
в APK автоматически.

## PNG из assets

Положите файл в `game/assets`, например `game/assets/player.png`. В скрипте имя
задаётся относительно этой папки:

```text
str PLAYER = "player.png"

fn init() {
    png_load(PLAYER) // необязательная предварительная загрузка
}

fn draw() {
    tex(100, 80, PLAYER, 0, 1)
}
```

`tex(x, y, name, angle, scale)` автоматически загружает и кэширует PNG при
первом вызове, поддерживает прозрачность, масштаб и поворот в радианах. `x` и
`y` — левый верхний угол изображения до поворота. Для подпапки используйте,
например, `"sprites/enemy.png"`.

Перед запуском `aapt` ресурсы нужно скопировать в каталог сборки. Для этого в
репозитории есть команда:

```sh
python3 stage_assets.py game/assets staging/assets
```

Она очищает старые ресурсы, сохраняет структуру подпапок и копирует содержимое
`game/assets` в корень assets будущего APK. Одного создания пустого
`staging/assets` недостаточно: без копирования PNG/TTF `png_load` и `text` не
найдут ресурсы внутри установленного приложения.

Готовый многофайловый пример находится в `examples/game_template`.

## Обработка ошибок и перезапуск

Каждый хук `init`, `update`, `draw` и `touch` запускается через
`ds_call_protected`. `ds_runtime_error` сохраняет сообщение и делает
контролируемый переход к границе вызова, поэтому повреждённое состояние не
продолжается до следующего кадра. Android-хост показывает безопасный экран
ошибки и автоматически пытается перезапустить скрипт через секунду: сначала
вызывается сгенерированный `reset`, затем `init`. Интерфейс также может вызвать
`ds_request_script_restart()` или `ds_restart_script()` для ручного перезапуска.

## Сборка в GitHub Actions

Воркфлоу `.github/workflows/main.yml` перед `aapt` копирует ресурсы в
`staging/assets`, а NDK-команда собирает software renderer (graphics.c с
встроенным TrueType-загрузчиком и runtime.c со строковыми утилитами) из
`game/game.c`, `runtime.c` и `main.c`. Для рендера не требуются `libEGL` и
`libGLESv2`.
